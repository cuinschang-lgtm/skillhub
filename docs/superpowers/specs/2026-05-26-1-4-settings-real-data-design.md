# SkillHub 1-4 Settings 页面真实数据接入设计

## 背景

在 `1-2` 完成后，SkillHub 前端已经建立了基础的数据层分层，但 `settings` 页面仍然停留在静态占位状态：

- 显示名称、邮箱、角色都是写死的假数据
- “保存修改”按钮没有真实提交逻辑
- 其他 tab（API Key、班级管理、额度与计费）也都是演示内容

这会带来两个实际问题：

- 用户无法判断当前登录身份是否正确
- `settings` 页面看起来像可用功能，但实际上不能读也不能写

相比 `chat` 会话管理或搜索 debounce，`settings` 的真实数据接入更适合作为一个独立、最小、可交付的 `1-4` 项。

## 目标

- 让 `settings` 页面至少有一个真实可用的“个人信息”tab
- 展示当前登录用户的真实资料：邮箱、角色、显示名
- 支持修改并保存 `display_name`
- 保持页面整体结构和现有路由不变
- 复用 `1-2` 已建立的 `types / api-client / hooks` 模式

## 非目标

- 不修改邮箱
- 不修改密码
- 不增加头像上传
- 不实现 API Key 管理
- 不实现班级管理真实接入
- 不实现额度与计费真实接入
- 不重做 `settings` 页面视觉样式

## 已确认事实

- 当前 `settings/page.tsx` 是纯静态页面，个人信息 tab 里的数据都是硬编码
- 浏览器侧当前已有 `GET /api/auth/me`，并能返回：
  - `email`
  - `role`
  - `displayName`
- 后端 `User` 模型当前已存在 `display_name` 字段
- 当前仓库里没有独立的“用户设置读写接口”
- 认证链路已经统一为 Bearer token + `httpOnly` cookie 透传，适合在当前用户上下文下做最小 profile 更新

## 设计原则

- 最小真实接入：先让最核心的资料读取与保存可用
- 不扩功能：只做当前模型已有字段，不借机扩成账户中心
- 保持兼容：不影响现有登录链路与 `/api/auth/me`
- 前后端分层：页面不直接手写 fetch，沿用 `1-2` 的数据层模式
- 明确边界：其他 tab 继续保留占位状态，但不伪装成已接通能力

## 方案选择

本次采用以下方案：

- 后端新增“当前用户 profile”最小读写接口
- 前端 `settings` 页面只把 `profile` tab 接成真实数据
- 前端新增对应 `types / api-client / hooks`
- 保存范围仅限 `display_name`

不采用以下方案：

- 不直接复用 `/api/auth/me` 做写入，因为它的职责更适合保持为“当前登录态查询”
- 不一次性打通 API Key、班级、计费三个 tab，因为这会让 `1-4` 明显扩范围
- 不在本次引入表单库或全局状态管理库

## 后端设计

### 新增接口

建议新增一组最小接口，用于读写当前用户资料：

- `GET /api/v1/settings/profile`
- `PATCH /api/v1/settings/profile`

职责：

- `GET`：返回当前登录用户的基础资料
- `PATCH`：更新当前用户的 `display_name`

### 返回字段

读取接口返回：

- `email`
- `role`
- `display_name`

写入接口返回：

- 更新后的同结构资料对象

### 更新范围

本次只允许更新：

- `display_name`

原因：

- `email` 同时承担身份标识语义，不适合在本轮引入修改链路
- `role` 是业务角色，不应由设置页自行改动

### 校验与错误处理

- 空字符串允许按产品约定处理为：
  - 去首尾空格后为空时，回退为 `NULL` 或空值
- 超长值应做长度限制，保持与 `User.display_name` 字段一致
- 接口错误返回清晰消息，不暴露内部实现细节

## 前端设计

### Settings 页

目标文件：

- `apps/web/src/app/(dashboard)/settings/page.tsx`

本次仅把 `profile` tab 接成真实可用：

- 初始加载时读取当前用户资料
- 展示真实的显示名、邮箱、角色
- 显示名支持编辑并保存
- 保存中按钮禁用，并给出明确反馈
- 保存成功后页面状态与输入状态同步更新

其余 tab 的处理：

- `API Key`
- `班级管理`
- `额度与计费`

继续保留现有占位 UI，但需要避免让用户误解为本轮已接通真实能力。

### 数据层

建议新增：

- `apps/web/src/types/settings.ts`
- `apps/web/src/lib/api-client/settings.ts`
- `apps/web/src/hooks/use-profile-settings.ts`

职责划分：

- `types`：承载 profile 数据结构与更新请求结构
- `api-client`：负责读取和更新 settings profile
- `hook`：负责 loading、error、saving、本地表单状态与提交流程

页面层只负责：

- 展示
- 输入绑定
- 调用保存动作

## 状态与反馈设计

页面至少应体现以下状态：

- 初始加载中
- 加载失败
- 正常编辑
- 提交中
- 提交成功
- 提交失败

反馈策略：

- 读取失败：在个人信息区块展示错误提示，不影响页面整体渲染
- 提交失败：保留用户输入，不覆盖为旧值
- 提交成功：更新本地显示值，并给出简洁成功提示

## 验收标准

- `settings` 页面不再显示硬编码的个人信息假数据
- 页面可展示当前登录用户的真实邮箱、角色、显示名
- 用户可修改并保存显示名
- 保存后刷新页面，仍能看到更新后的显示名
- 其余 tab 不被误认为本轮已完成真实接入
- 前端 `lint` 通过
- 不影响现有认证与 `/api/auth/me` 行为

## 测试与验证

后端至少验证：

- 已登录用户可读取 profile
- 已登录用户可更新 `display_name`
- 非法输入会收到明确错误

前端至少验证：

- `settings` 页面可正常加载 profile 数据
- 保存按钮在提交中禁用
- 保存成功后显示最新值
- 保存失败时保留输入并展示错误
- `npm run lint` 通过

## 风险与缓解

风险：

- 如果页面直接把所有 tab 都改成“真实功能待实现”，可能影响当前演示体验
- 若更新接口与 `/api/auth/me` 字段命名不一致，容易造成前端状态混乱
- 如果不控制范围，`settings` 容易扩展成新的大模块

缓解：

- 本次仅接通 `profile` tab
- 明确统一前后端字段映射关系
- 保持保存范围仅限 `display_name`
